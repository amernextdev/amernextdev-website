# decision-engine.md

## الهدف
توفير بروتوكول تشغيلي واضح لتقييم أي قرار تنفيذي.
يُزيل الاجتهاد عند نقطة القرار ويُسرّع الرفض أو القبول.

## المشمول
- تسلسل بوابات التقييم
- معيار القبول والرفض لكل بوابة
- أمثلة تطبيقية على حالات قرار شائعة

## غير المشمول
- القوانين نفسها (→ `non-negotiable-laws.md`)
- آلية حسم التعارض بين مبدأين صالحين (→ `conflict-resolution.md`)
- أوضاع الفشل على مستوى المنظومة (→ `risk-landscape.md`)

## البروتوكول

كل قرار — تصميم، محتوى، ميزة، كود — يمر عبر البوابات بالتسلسل.
"لا" عند أي بوابة يُنهي المقترح. لا تُكمل.

---

### البوابة 1 — القوانين غير القابلة للتفاوض
**السؤال:** هل يتعارض هذا مع أي قانون في `non-negotiable-laws.md`؟

- **نعم** → رفض فوري. لا تداول.
- **لا** → انتقل للبوابة 2.

---

### البوابة 2 — أمان الهجرة
**السؤال:** هل يُعيق هذا الانتقال النظيف إلى المرحلة الثالثة (React/API)؟

الفحوصات:
- هل يُضيف اقتراناً بين مكونات يجب أن تبقى معزولة؟
- هل يُشفّر محتوى في الترميز بدل JSON؟
- هل يُخالف نمط ES6 modules؟
- هل يُعرّف متغيرات CSS خارج كتلة `:root`؟

- **نعم لأي منها** → رفض. تكلفة الهجرة تُدفع الآن.
- **لا لكلها** → انتقل للبوابة 3.

---

### البوابة 3 — نزاهة التموضع
**السؤال:** هل يُضعف هذا إشارة الثقة أو يُخفف التمايز؟

الفحوصات:
- هل يُقرّب الموقع من شكل portfolio نمطي؟
- هل يُرسل إشارة "متاح للجميع" بدل "انتقائي"؟
- هل يُضيف ضوضاء بصرية أو معلوماتية؟
- هل اللغة غامضة أو متحمسة بدل دقيقة وهادئة؟

- **نعم لأي منها** → رفض. نزاهة التموضع لا تُخفَّف لثراء الميزات.
- **لا لكلها** → انتقل للبوابة 4.

---

### البوابة 4 — ميزانية الأداء
**السؤال:** هل يتجاوز هذا أي سقف في `performance-budget.md`؟

الفحوصات:
- هل يُضيف وزناً لـ DOM غير مبرر؟
- هل يُضيف JS يعيق العرض؟
- هل يُضيف تبعية CDN خارجية جديدة؟
- هل تحميل الصور غير محسوب؟

- **نعم لأي منها** → رفض أو تعديل جوهري قبل إعادة التقييم.
- **لا لكلها** → انتقل للبوابة 5.

---

### البوابة 5 — أناقة الكود
**السؤال:** هل هذا التنفيذ هو الأنظف لتحقيق الهدف؟

الفحوصات:
- هل هناك طريقة أبسط بعائد مكافئ؟
- هل التوثيق المضمن موجود (الغرض، القيود، ملاحظة الهجرة)؟
- هل التسمية دلالية وتتبع BEM أو معادله؟

- **لا** → أعد الكتابة قبل الدمج.
- **نعم** → قرار: **مقبول**.

---

## أمثلة تطبيقية

### مثال 1 — طلب إضافة زر "تواصل الآن" بارز
- بوابة 1: يُرسل إشارة "متاح الآن" → **رفض (Q2)**

### مثال 2 — إضافة تأثير hover بـ inline style لسرعة التنفيذ
- بوابة 1: لا تعارض مباشر
- بوابة 2: inline style يُخالف مبدأ الفصل → **رفض (T1)**

### مثال 3 — استخدام مكتبة animation خارجية
- بوابة 1: لا تعارض
- بوابة 2: لا تعيق الهجرة إذا كانت معزولة
- بوابة 3: لا تُضعف التموضع
- بوابة 4: **تُضيف حمولة JS** — هل العائد يبرر؟ إذا لا → **رفض (T2)**

## القيود التي يجب مراعاتها
- البروتوكول يُطبَّق بالتسلسل دائماً. لا تخطي بوابة
- "الاستثناء لمرة واحدة" غير موجود
- القرارات الصغيرة (تغيير كلمة في محتوى، تعديل لون بالقيمة المحددة) لا تحتاج المرور بكل البوابات — البوابة 1 تكفي

## التأثير على التطبيق
يُنتج هذا البروتوكول قرارات سريعة وموثّقة.
كل رفض له مرجع واضح: رقم البوابة والقانون أو المعيار المنتهَك.
