# review-process.md

## الهدف
تحديد عملية المراجعة الدورية للمنظومة — ما يُراجَع، متى، وكيف تُوثَّق النتائج.

## المشمول
- أنواع المراجعات وتواترها
- قائمة الفحص لكل نوع مراجعة
- قالب توثيق نتائج المراجعة
- كيف تؤدي المراجعة إلى إجراء

## غير المشمول
- معايير إضافة المحتوى وتحديثه (→ `content-governance.md`)
- بروتوكول التغييرات التقنية (→ `change-request-protocol.md`)
- عملية Lighthouse (→ `lighthouse-validation-process.md`)

## أنواع المراجعات

### 1 — المراجعة الشهرية (30 دقيقة)

**التركيز:** الأداء الفعلي والمحتوى.

```
ANALYTICS (إذا تتبع):
[ ] ما الصفحات الأكثر زيارة؟
[ ] ما مصادر الزيارات الرئيسية؟
[ ] هل هناك نقطة تخلٍّ واضحة؟

CONTENT:
[ ] هل هناك مشروع منجز يستحق إضافته؟
[ ] هل أي بيانات موجودة تحتاج تحديثاً (metrics، تواريخ)؟

TECHNICAL:
[ ] هل هناك 404 جديدة في Search Console؟
[ ] هل شهادة SSL لا تزال صالحة؟
[ ] هل هناك تبعيات خارجية تحتاج تحديث الإصدار؟

RISK:
[ ] هل ظهرت أي أعراض من risk-landscape.md؟
```

---

### 2 — المراجعة الربع سنوية (2 ساعة)

**التركيز:** التموضع وأوضاع الفشل.

```
POSITIONING:
[ ] هل بيان التموضع لا يزال يعكس الواقع؟
[ ] هل المشاريع المعروضة لا تزال الأفضل للتمايز؟
[ ] هل آليات التصفية تعمل؟ (جودة التواصل الوارد)

RISK AUDIT (كل بند من risk-landscape.md):
[ ] R1 — لا انجراف نحو portfolio نمطي
[ ] R2 — آليات التصفية سليمة
[ ] R3 — اللغة محتفظة بدقتها
[ ] R4 — لا دين تقني غير موثَّق
[ ] R5 — Lighthouse ضمن الميزانية
[ ] R6 — معيار عزل المكونات محفوظ
[ ] R7 — لا محتوى يتيم
[ ] R8 — لا تضخم في الصفحة

CONTENT AUDIT (content-governance.md):
[ ] هل المشاريع المعروضة لا تزال ≤ 5؟
[ ] هل كل مشروع يُظهر كفاءة مختلفة؟
[ ] هل profile.json يعكس المنهجية الحالية؟

EVOLUTION:
[ ] هل شروط الانتقال للمرحلة التالية اقتربت؟ (→ evolution-matrix.md)
```

---

### 3 — المراجعة السنوية (نصف يوم)

**التركيز:** الاستراتيجية الكاملة.

```
CONSTITUTION:
[ ] هل master-constitution.md لا يزال يعكس الهدف الاستراتيجي الفعلي؟
[ ] هل هناك قانون في non-negotiable-laws.md يحتاج تحديثاً بناءً على تجربة السنة؟
[ ] هل conflict-resolution.md يحتاج إضافة أمثلة جديدة من القرارات المتراكمة؟

POSITIONING:
[ ] هل المقيّم المستهدف تغيّر أو تطوّر؟ (→ client-psychology-model.md)
[ ] هل بيان التموضع يعكس المرحلة التطورية الحالية؟

TECHNICAL DEBT:
[ ] ما الديون التقنية المتراكمة الموثّقة؟
[ ] هل أي منها يستلزم معالجة قبل الانتقال للمرحلة التالية؟

EVOLUTION READINESS:
[ ] ما أقرب مرحلة تطور قادمة؟
[ ] هل الشروط المسبقة جاهزة؟ (→ evolution-matrix.md)
[ ] هل الوثائق المرتبطة محدّثة؟
```

يُحفظ في `reports/reviews/[date]-[type]-review.md`:

```markdown

[جملة أو جملتان عن الحالة العامة]

### ما يعمل بشكل جيد
- [بند]
- [بند]

### ما يحتاج معالجة
| البند | الأولوية | الإجراء | الموعد |
|------|---------|---------|--------|
| [بند] | عالية/متوسطة/منخفضة | [ماذا] | [متى] |

### قرارات اتُّخذت
- [قرار] ← [سببه]

### الإجراءات المُخطَّطة

[أي شيء يُراقَب في المراجعة القادمة]
```

## كيف تؤدي المراجعة إلى إجراء

```
نتيجة المراجعة → تصنيف الإجراء → المسار

مشكلة تقنية    → change-request-protocol.md النوع ب أو ج
محتوى يحتاج تحديث → content-governance.md + النوع أ
وضع فشل مكتشف  → risk-landscape.md + إجراء فوري
قرار استراتيجي → change-request-protocol.md النوع د
انتقال مرحلة   → evolution-matrix.md + خطة الانتقال المناسبة
```

## جدولة المراجعات

| النوع | التاريخ المقترح |
|------|----------------|
| شهرية | أول أسبوع من كل شهر |
| ربع سنوية | يناير، أبريل، يوليو، أكتوبر |
| سنوية | الذكرى السنوية للإطلاق |

المراجعات ليست اختيارية عند نسيانها — كل مراجعة فائتة تعني أوضاع فشل لم تُكشَف.

## القيود التي يجب مراعاتها
- المراجعة التي لا تُنتج أي ملاحظة ليست مراجعة — إما المنظومة في حالة ممتازة (يُوثَّق) أو المراجعة سطحية
- لا مراجعة بدون توثيق نتائجها. التوثيق هو قيمة المراجعة.

## التأثير على التطبيق
هذه العملية هي آلية الحفاظ على نزاهة المنظومة عبر الزمن.
بدونها، التراكم الصغير يُفضي للانجراف الذي تُحذّر منه `risk-landscape.md`.

## وثائق مرتبطة
- `risk-landscape.md` (← `01-constitution/`) — قائمة أوضاع الفشل التي تفحصها المراجعة
- `content-governance.md` — معايير المحتوى المُراجَعة شهرياً
- `evolution-matrix.md` (← `05-evolution/`) — شروط الانتقال المُراجَعة سنوياً
- `change-request-protocol.md` — مسار الإجراءات الناتجة عن المراجعة
