# content-governance.md

## الهدف
تحديد قواعد إضافة المحتوى وتحديثه وإزالته — من يملك القرار، وكيف يُتحقق منه.

## المشمول
- أنواع المحتوى وملكية القرار فيه
- معايير إضافة مشروع جديد
- معايير تحديث المحتوى الموجود
- معايير إزالة المحتوى
- دورة مراجعة المحتوى الدورية

## غير المشمول
- قواعد اللغة المفصّلة (→ `language-governance.md`)
- بروتوكول التغييرات التقنية (→ `change-request-protocol.md`)
- مخططات JSON (→ `json-content-schema.md`)

## أنواع المحتوى وملكية القرار

| نوع المحتوى | الملف | معيار التغيير |
|------------|-------|--------------|
| المشاريع المعروضة | `portfolio.json` | يخدم إطار: مشكلة ← قرار ← نتيجة |
| بيان التموضع | `profile.json` | لا يتغير إلا بقرار استراتيجي موثَّق |
| منهجية العمل | `profile.json` | يتغير بتطور فعلي في طريقة العمل |
| آلية التواصل | `config.json` | يتغير حسب القناة الفعلية المتاحة |
| نصوص الموقع | HTML أو JSON | يتبع language-governance.md |

## معايير إضافة مشروع جديد

مشروع يُضاف إلى portfolio.json إذا استوفى **جميع** المعايير التالية:

### معيار 1 — القيمة المعمارية
المشروع يُظهر **قراراً معمارياً** حقيقياً يمكن توضيحه بإطار: مشكلة ← قرار ← نتيجة.
مشروع تنفيذي بدون قرار معماري لا يُضاف بغض النظر عن حجمه أو العميل.

### معيار 2 — التمايز من المشاريع الموجودة
المشروع الجديد يُظهر بُعداً أو سياقاً **لا تُغطيه المشاريع الموجودة**.
إضافة مشروع مشابه لمشروع قائم تُضعف التموضع بدل تقويته.

### معيار 3 — الحد الأقصى للمعروض
عدد المشاريع المعروضة (status: featured) لا يتجاوز **5 مشاريع** في أي وقت.
إضافة مشروع سادس تستلزم إزالة أو تحويل مشروع موجود إلى status: archived.

### معيار 4 — اكتمال البيانات
كل حقل مطلوب في `json-content-schema.md` مُملوء.
لا مشروع بـ `"summary": "قريباً"` أو حقل فارغ.

### قالب التحقق قبل الإضافة
```
[ ] المشروع يُظهر قراراً معمارياً محدداً
[ ] يختلف تماماً عن المشاريع الموجودة في نوع الكفاءة التي يُظهرها
[ ] العدد الإجمالي المعروض لن يتجاوز 5 بعد الإضافة
[ ] جميع الحقول مكتملة بمحتوى نهائي
[ ] decision.alternatives_rejected يحتوي بديلاً واحداً على الأقل
[ ] outcome.metrics يحتوي رقماً واحداً على الأقل (أو وصفاً لا يمكن قياسه)
[ ] اللغة تتبع language-governance.md
```

## معايير تحديث المحتوى الموجود

### تحديثات مسموحة بدون مراجعة استراتيجية
- تصحيح خطأ إملائي أو نحوي
- تحديث رقم أو تاريخ بيانات موثوق
- إضافة metric جديد لمشروع مكتمل

### تحديثات تستلزم مراجعة
- إعادة صياغة decision.summary أو outcome.summary لمشروع
- تغيير problem.summary بطريقة تُغيّر طبيعة المشكلة
- تغيير profile.identity.positioning_statement

**المراجعة تعني:** التحقق من توافق النص الجديد مع `language-governance.md` وعدم خروجه عن `identity-translation-layer.md`.

## معايير إزالة المحتوى

### إزالة مشروع من Featured
```
status: "featured" → status: "archived"
```
يُستخدم حين:
- مشروع لم يعد يُمثّل الكفاءة المُراد إظهارها
- مشروع جديد أفضل يحل محله
- عدد المشاريع المعروضة يتجاوز 5

**لا يُحذف من JSON** — يُحوَّل لـ archived للحفاظ على التاريخ.

### إزالة محتوى من profile.json
تغيير في focus_areas أو process.phases يستلزم مراجعة: هل التغيير يعكس تطوراً حقيقياً في طريقة عمل عامر، أم هو تحسين بلاغي؟ الثاني لا يُبرر التغيير.

## دورة المراجعة الدورية

### ربع سنوية (كل 3 أشهر)
```
[ ] هل المشاريع المعروضة لا تزال تُمثّل أفضل ما يُظهر الكفاءة الحالية؟
[ ] هل هناك مشروع منجز يستحق الإضافة؟
[ ] هل profile.identity.positioning_statement لا يزال دقيقاً؟
[ ] هل آلية التواصل في config.json لا تزال صحيحة؟
```

### سنوية (مع كل مرحلة تطور)
```
[ ] هل بيان التموضع يعكس المرحلة الجديدة؟
[ ] هل المشاريع القديمة تتوافق مع التموضع الجديد؟
[ ] هل process.phases يعكس المنهجية الفعلية الحالية؟
```

## القيود التي يجب مراعاتها
- المحتوى الجيد لا يُضاف لأنه موجود — يُضاف لأنه يخدم التموضع
- "نادراً ما تكون إضافة محتوى قراراً سيئاً" — هذا خطأ في سياق هذه المنظومة. الإضافة دائماً تُقيَّم.

## التأثير على التطبيق
هذه الوثيقة هي الفلتر اليومي للمحتوى.
كل "هل أضيف هذا المشروع؟" يُجيب عنه المعايير الأربعة، لا التقدير الشخصي.
