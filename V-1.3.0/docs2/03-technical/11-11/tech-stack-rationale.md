## المكدس التقني للمرحلة الأولى

### HTML — الهيكل

**الاختيار:** HTML5 دلالي، ملفات `.html` ثابتة.

**المبرر:**
- موقع المرحلة الأولى محتواه ثابت. لا حاجة لأي طبقة توليد ديناميكي.
- HTML دلالي هو الأساس الذي تُبنى عليه إمكانية الوصول وSEO والكود النظيف.
- الملفات الثابتة تعني أداءً أقصى بلا طبقة خادم.

**البديل المرفوض:** Static site generator (Jekyll، Hugo، Eleventy).
**مسوّغ الرفض:** يُضيف تبعية وعملية بناء لمحتوى لا يتجاوز 5 صفحات. العائد لا يبرر التعقيد في المرحلة الأولى.

**متطلب الهجرة:** بنية الصفحات يجب أن تعكس structure مكونات React المستقبلية — قسم واحد لكل مكون.

---

### CSS — العرض

**الاختيار:** CSS خالص، ملف مُجمَّع واحد في الإنتاج، متغيرات CSS في `:root`.

**المبرر:**
- CSS خالص بمتغيرات يُحقق كل متطلبات التصميم دون تبعيات.
- ملف واحد في الإنتاج يُلغي طلبات HTTP إضافية.
- المتغيرات في `:root` تُمكّن تغيير النظام الكامل بتعديل موضع واحد — وهي نفس البنية التي ستُصدَّر لاحقاً كـ design tokens في المرحلة الثانية.

**البديل المرفوض:** Tailwind CSS.
**مسوّغ الرفض:** يُدخل تبعية بناء وفلسفة utility-first تتعارض مع معيار عزل المكونات. فصل CSS عن HTML يصبح مستحيلاً. الهجرة إلى React ستستلزم إعادة كتابة كاملة لطبقة التصميم.

**البديل المرفوض:** CSS-in-JS (styled-components، emotion).
**مسوّغ الرفض:** مرفوض بالبديهية الثانية. يكسر فصل المسؤوليات ويجعل استخراج مكونات نظيفة أصعب.

**متطلب الهجرة:** متغيرات CSS الحالية تُصدَّر كـ design tokens في المرحلة الثانية. البنية موجودة.

---

### JavaScript — السلوك

**الاختيار:** JavaScript خالص، ES6+ modules، بدون إطار عمل.

**المبرر:**
- موقع المرحلة الأولى لا يحتاج state management معقداً. تفاعلات بسيطة (navigation، form submission) تُحقَّق بـ vanilla JS.
- ES6 modules تضمن عزل الفضاء الأسمائي وتُسهّل الهجرة إلى React components.
- لا JS يعيق العرض: جميع scripts مُؤجَّلة أو async.

**البديل المرفوض:** React في المرحلة الأولى.
**مسوّغ الرفض:** يُضيف حزمة ومعقدية لمحتوى ثابت. الفائدة الحقيقية لـ React تأتي مع الديناميكية والحالة — وهو دور المرحلة الثالثة.

**البديل المرفوض:** jQuery.
**مسوّغ الرفض:** تبعية غير مبررة. كل وظيفة jQuery المطلوبة قابلة للتحقيق بـ vanilla ES6 بجهد مكافئ.

**متطلب الهجرة:** كل وحدة JS يجب أن تُكتب بحيث يمكن استخراج منطقها إلى React custom hook بتعديلات طفيفة.

---

### إدارة المحتوى

**الاختيار:** ملفات JSON محلية.

**المبرر:**
- المحتوى مفصول عن الترميز (البديهية الثالثة).
- مخططات JSON الحالية تعكس أشكال API المستقبلية — الهجرة لاحقاً تعني استبدال `fetch('./data.json')` بـ `fetch('api/endpoint')`.

**البديل المرفوض:** CMS (Contentful، Sanity، WordPress).
**مسوّغ الرفض:** تبعية خارجية وتعقيد إدارة غير مبررَين لمحتوى لا يتغير يومياً. المرحلة الخامسة ستُقيّم الحاجة لـ CMS حين يكون حجم المحتوى يستدعيه.

---

### الاستضافة والنشر

**الاختيار:** استضافة ثابتة (Netlify، Vercel، أو GitHub Pages).

**المبرر:**
- لا خادم = لا صيانة خادم، لا نقطة فشل إضافية، أداء أقصى عبر CDN.
- ملفات ثابتة تعني deployment فوري بدون pipeline معقدة.

**متطلب الهجرة:** عند الانتقال للمرحلة الثالثة، الاستضافة الثابتة لا تزال صالحة لـ Next.js في وضع SSG. لا تغيير جوهري مطلوب.

### التبعيات الخارجية المقبولة

| التبعية | الوظيفة | المبرر |
|---------|---------|--------|
| FontAwesome | أيقونات SVG | لا بديل مكافئ بجهد أقل. يُستخدم من CDN مع تحديد الإصدار. |
| Google Fonts (اختياري) | خطوط الطباعة | مقبول إذا لم تتوفر نسخ محلية. يُستخدم مع `font-display: swap` وتحديد الإصدار. |
