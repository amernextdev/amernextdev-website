## البديهية الأولى — البساطة كانضباط

**البيان:** البساطة ليست غياب التعقيد — بل نتيجة تعقيد مُحلول.

**المسوّغ:** كل عنصر في الكود موجود لأنه اجتاز تبريراً. HTML/CSS/JS النظيف في المرحلة الأولى ليس قيداً على القدرة — بل دليل على أن التعقيد لا يُدخَل إلا حين يُكتسب.

**الانعكاس التنفيذي:**
- قبل إضافة أي عنصر: "ما الذي يتوقف عمله إذا حذفت هذا؟"
- إذا كانت الإجابة "لا شيء" — يُحذف.
- التبسيط مسؤولية مستمرة، لا قرار يُتخذ مرة واحدة.

**اختبار التحقق:** هل يمكن شرح كل سطر كود بجملة واحدة تصف وظيفته؟ إذا لا — إعادة كتابة.

## البديهية الثانية — فصل المسؤوليات كبنية

**البيان:** HTML يحكم البنية. CSS يحكم العرض. JavaScript يحكم السلوك.

**المسوّغ:** هذا الفصل ليس أسلوبياً — بل شرط مسبق لاستخراج مكونات React في المرحلة الثالثة. كل اقتران بين الطبقات اليوم هو تكلفة إعادة كتابة تُدفع لاحقاً.

**الانعكاس التنفيذي:**
- لا `style=""` مضمنة في HTML إلا لقيم ديناميكية يُنتجها JS حصراً.
- لا CSS-in-JS في أي شكل.
- لا تعديل مباشر للـ style من JS — الحالة البصرية تُدار عبر إضافة/إزالة classes أو data attributes.
- لا سلوك مُشفَّر في HTML (event handlers في الترميز).

**اختبار التحقق:** هل يمكن استبدال ملف CSS كامل دون لمس HTML أو JS؟ إذا لا — يوجد اقتران يجب معالجته.

## البديهية الثالثة — جاهزية التجريد كتوافق مستقبلي

**البيان:** ما يُشفَّر اليوم هو دَين تقني يُدفع في الهجرة.

**المسوّغ:** كل اقتران يُدخَل الآن هو تكلفة هجرة مدفوعة لاحقاً. الهدف ليس التجريد الكامل من اليوم الأول — بل عدم خلق اقترانات لا مسوّغ لها.

**الانعكاس التنفيذي:**
- المحتوى في JSON، لا مُشفَّراً في HTML.
- متغيرات CSS في كتلة `:root` واحدة، لا مبعثرة.
- منطق العرض لا يتشابك مع منطق البيانات.
- مخططات JSON تعكس أشكال استجابة API المتوقعة — لا هياكل مسطحة اعتباطية.

**اختبار التحقق:** هل يمكن استبدال ملف JSON بـ API call دون تغيير في منطق العرض؟ إذا لا — يوجد اقتران يجب معالجته.

## البديهية الرابعة — لا تبعية دون عائد مبرر

**البيان:** كل تبعية خارجية تُدخل سطح صيانة، ومخاطر إصدار، وتكلفة حزمة.

**المسوّغ:** التبعية مبررة فقط حين تُقدم عائداً لا يمكن تكراره بجهد تطبيق مكافئ أو أقل.

**اختبار قبول التبعية:**
1. ما الوظيفة التي تُقدمها؟
2. هل يمكن تنفيذ هذه الوظيفة بكود مخصص في وقت مكافئ؟
3. هل حجمها يتجاوز ما تستحقه وظيفتها؟
4. هل تُضيف مخاطر أمنية أو توافق لاحق؟

إذا فشلت في أي سؤال — تُرفض.

**الحالات المقبولة في المرحلة الأولى:**
- FontAwesome: أيقونات SVG محسنة، لا بديل مكافئ بجهد أقل.
- خطوط Google أو خطوط محلية: مبررة بجودة الطباعة.

**الحالات المرفوضة:**
- إطار UI كامل (Bootstrap، Tailwind) للمرحلة الأولى: يُدخل تعقيداً أكبر من عائده على موقع ثابت.
- مكتبة animation خارجية لتأثيرات يمكن تحقيقها بـ CSS transitions.

**اختبار التحقق:** هل يمكن إزالة هذه التبعية دون إعادة بناء جوهرية؟ إذا لا — التبعية اقتران مخفي يجب توثيقه أو تجنبه.

## العلاقة بين البديهيات

البديهيات الأربع متكاملة:
- **الأولى** تُقلل ما يُبنى.
- **الثانية** تُنظّم كيف يُبنى.
- **الثالثة** تضمن أن ما يُبنى قابل للتطور.
- **الرابعة** تُقلل ما يُعتمد عليه.

انتهاك أي منها يُنقص من قيمة الثلاث الأخرى.

## القيود التي يجب مراعاتها
- البديهيات ثابتة عبر المراحل — لا تتغير بتغيير المكدس التقني.
- الاستثناء المؤقت يصبح ديناً تقنياً. إذا أُضيف استثناء، يُوثَّق فوراً في `git-workflow.md` مع خطة السداد.

## التأثير على التطبيق
قبل كتابة أي كود، السؤال: "أي بديهية تحكم هذا القرار وكيف؟"
الكود الذي لا يمكن ربطه ببديهية واضحة إشارة لإعادة التفكير.
