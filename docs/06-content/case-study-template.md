# 📁 case-study-template.md — قالب دراسة الحالة

> "دراسة الحالة الجيدة لا تُثبت ما تستطيع فعله — تُثبت كيف تُفكّر."

---

## 1️⃣ لماذا دراسة الحالة أهم من Portfolio

معرض الأعمال يجيب على: "هل رأيت هذا من قبل؟"
دراسة الحالة تجيب على: "هل تعرف كيف تحل هذا؟"

السؤال الثاني هو ما يُهم العميل الجاد. يريد أن يعرف:
- هل يفهم المطور مشاكل مثل مشكلتي؟
- هل يتخذ قرارات مدروسة أم عشوائية؟
- هل سيتصرف صح حين تتعقد الأمور؟

دراسة الحالة تُجيب على الثلاثة. screenshot لا يُجيب على أي منها.

---

## 2️⃣ معايير اختيار المشاريع للتوثيق

### اختر المشروع إذا:

```
✅ المشكلة التي حلّها تُشبه مشاكل العملاء المستهدفين
✅ اتخذت فيه قرارات غير بديهية يمكن شرحها
✅ النتيجة قابلة للوصف حتى لو لم تكن رقمية
✅ العميل أذن بالنشر (ولو بدون اسمه)
✅ يُثبت جانباً من الخدمات المعلنة في `services-framework.md`
```

### لا تختره إذا:

```
❌ كان تنفيذاً بحتاً بلا قرارات مثيرة للشرح
❌ المشكلة شائعة جداً ولا تُميّز
❌ لا يمكن الكشف عن تفاصيل كافية للقصة
❌ لا يمثل نوع العمل الذي تريد استقطابه
```

## 3️⃣ هيكل دراسة الحالة الكاملة

---

### القسم 1 — الـ Header (الرأس)

**ما يظهر:**
```
[Project Label — نوع المشروع: "Web App" | "Website" | "Dashboard"]
[Project Title — اسم المشروع أو وصف موجز للمخرج]
[Project Tagline — جملة واحدة تصف جوهر التحدي]
[Cover Image — صورة تمثّل المشروع بصرياً]
```

**Project Meta (جدول سريع):**
```
الدور:     [ما قمتَ به تحديداً]
المدة:     [أسابيع/أشهر تقريبية]
التقنيات: [فقط الرئيسية المرتبطة بقرار]
الحالة:    [مُطلَق | قيد التطوير | Prototype]
```

**قاعدة كتابة Tagline:**
```
لا: "موقع احترافي لشركة X"
نعم: "تحويل نظام تسجيل ورقي إلى منصة رقمية تُعالج ١٠٠+ طلب يومياً"
```

---

### القسم 2 — Overview (نظرة عامة)

**الهدف:** الإجابة على "ما هذا؟" و"لمن؟" في 60 ثانية.

**ما يُكتب (3–5 جمل):**
```
- من كان العميل؟ (القطاع، حجم العمل — بدون اسم إذا لزم)
- ما السياق التجاري للمشروع؟
- لماذا كان هذا المشروع ضرورياً في تلك اللحظة؟
```

**مثال على الأسلوب:**
```
"شركة خدمات محاسبية صغيرة (5–10 موظفين) كانت تدير
عمليات تسليم التقارير عبر البريد الإلكتروني والجداول
الورقية. مع نمو قاعدة العملاء، أصبح النظام عائقاً لا
أداة — يضيع في كل أسبوع ساعات لإدارة ما يمكن أتمتته."
```

---

### القسم 3 — The Problem (المشكلة)

**الهدف:** إثبات أنك فهمت المشكلة الحقيقية — لا الأعراض.

**هيكل الكتابة:**

**المشكلة الظاهرة (ما قاله العميل):**
```
ما الذي طلبه العميل في البداية؟
```

**المشكلة الحقيقية (ما اكتشفتَه):**
```
بعد الفهم الكافي، ما كانت المشكلة الجذرية؟
هل كانت مختلفة عما طُلب في البداية؟
```

**القيود:**
```
ما الحدود التي فُرضت على الحل؟
(الميزانية، الجدول الزمني، تقنيات موجودة، مستخدمون بدون خبرة تقنية...)
```

**مثال:**
```
المشكلة الظاهرة: "نريد موقعاً يعرض خدماتنا."
المشكلة الحقيقية: العملاء الجدد لا يُكملون عملية التواصل
بسبب غموض الخطوة التالية — الموقع يُعرّف لكن لا يُحوّل.
القيود: لا ميزانية لإعادة تصميم هوية كاملة — الحل ضمن التصميم القائم.
```

---

### القسم 4 — Approach & Decisions (المنهجية والقرارات)

**الهدف:** هذا القسم هو قلب دراسة الحالة — يُظهر التفكير لا التنفيذ.

**هيكل الكتابة:**

**خطوات المنهجية:**
```
كيف اقتربتَ من المشكلة؟
ما الخطوات التي مررتَ بها قبل الكتابة الأولى؟
```

**القرارات الرئيسية (الجوهر):**
لكل قرار مهم:

```
القرار: [ماذا اخترتَ؟]
البديل: [ما الذي كان يمكن اختياره بدلاً؟]
المبرر: [لماذا هذا تحديداً؟]
التأثير: [ما الذي أتاحه هذا القرار؟]
```

**مثال:**
```
القرار:  بناء نظام Stateless بدلاً من Session-based
البديل:  Sessions تقليدية كانت أسرع في التنفيذ
المبرر:  العميل يخطط لتوسيع الفريق — JWT يُتيح ذلك بدون إعادة بناء Auth
التأثير: الـ API أصبح قابلاً للتوسع لتطبيق موبايل مستقبلياً
```

**اللحظات الصعبة (اختياري لكن قوي):**
```
ما المشكلة التي لم تتوقعها وكيف تعاملتَ معها؟
```

---

### القسم 5 — Solution (الحل)

**الهدف:** عرض المخرج النهائي مع ربطه بقرارات القسم السابق.

**ما يُعرض:**
- Screenshots مع captions وصفية تشرح الـ "لماذا" لا الـ "ماذا"
- إذا كان كوداً: مقتطفات تُظهر قرارات التصميم — لا الكود الكامل
- إذا كان تصميماً: قبل/بعد مع شرح الفرق الوظيفي

**قاعدة الـ Caption:**
```
❌ "الصفحة الرئيسية للتطبيق"
✅ "لوحة التحكم مصممة لعرض 3 مقاييس فقط — بناءً على تحليل
    ما يحتاجه مدير العمليات فعلياً في بداية يومه"
```

---

### القسم 6 — Outcome (النتيجة)

**الهدف:** قياس النتيجة بأمانة — أرقام حيث يُؤذن، وصف حيث لا.

**هيكل الكتابة:**

**النتائج الموضوعية:**
```
إذا توفرت أرقام (بإذن العميل):
  "وقت المعالجة اليدوية انخفض من 4 ساعات/يوم إلى 40 دقيقة"
  "معدل إكمال نموذج التواصل ارتفع بنسبة 35%"

إذا لم تتوفر أرقام:
  "النظام يُعالج الآن جميع طلبات التسجيل دون تدخل يدوي"
  "الفريق قادر على تحديث المحتوى بدون الحاجة لمطور"
```

**التقييم الذاتي (ضروري):**
```
"ما الذي كنت سأفعله بشكل مختلف؟"
```

هذا السؤال ليس اعترافاً بالفشل — هو دليل على النضج المهني والوعي الذاتي. يُعزز الثقة لا يُضعفها.

---

### القسم 7 — CTA (الدعوة)

```
"لديك مشروع مشابه؟ تحدث معنا."

أو بشكل أكثر تحديداً:
"إذا كنت تواجه [نوع المشكلة المذكورة في الدراسة]،
 هذه تحديداً أنواع المشاريع التي أعمل عليها."
```

## 5️⃣ قائمة المراجعة قبل النشر

```
☐ الـ Tagline تصف التحدي — لا المخرج
☐ المشكلة الحقيقية مختلفة أو أعمق من المشكلة الظاهرة
☐ كل قرار موثّق بـ: القرار + البديل + المبرر + التأثير
☐ الـ Captions تشرح "لماذا" لا "ماذا"
☐ النتيجة موضوعية — لا مبالغة ولا تقليل
☐ التقييم الذاتي موجود وصادق
☐ العميل أذن بالنشر (حتى لو بشكل مجهول)
☐ الدراسة تُثبت خدمة موجودة في `services-framework.md`
☐ CTA في النهاية يربط بنوع المشكلة المذكورة
```

## 6️⃣ أخطاء شائعة في دراسات الحالة

| الخطأ | الأثر | التصحيح |
|---|---|---|
| التركيز على الكود لا على القرار | يُقنع المطورين لا العملاء | اشرح "لماذا" لا "كيف" |
| نتائج مضخّمة | يكسر الثقة عند من يعرف | أرقام صادقة أو وصف بدون أرقام |
| غياب التقييم الذاتي | يبدو الموقع مصقولاً بشكل مصطنع | جملتان عن ما ستُحسّنه |
| Screenshots بلا سياق | لا تُفيد العميل غير التقني | Caption يشرح القرار وراء الصورة |
| قصة طويلة جداً | تُفقد القارئ التركيز | حد أقصى 800–1000 كلمة |
