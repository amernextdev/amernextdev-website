## تعريف Client Portal

Client Portal هو البيئة الرقمية التي يتفاعل فيها عملاء عامر مع مشاريعهم الجارية.
هو تحويل العلاقة من "بريد إلكتروني + مستندات" إلى نظام شفاف ومنظَّم.

**الوظيفة الأساسية:** العميل يدخل بمعرّفه، يرى حالة مشروعه، يُراجع التسليمات، يُوافق على المراحل — كل ذلك في مكان واحد.

## المتطلبات الوظيفية

### لوحة تحكم العميل (Client Dashboard)
- حالة المشروع الحالية (المرحلة، النسبة المئوية، الموعد المتوقع)
- قائمة التسليمات مع حالة كل منها (مُعلَّق، للمراجعة، مُعتمَد)
- سجل التحديثات والقرارات
- قناة تواصل مباشرة (بديل البريد للمحادثات المرتبطة بالمشروع)

### إدارة المشاريع (Admin — لعامر فقط)
- إنشاء/تحديث المشاريع والمراحل
- رفع التسليمات ومشاركتها مع العميل
- إضافة تحديثات وملاحظات
- تتبع الموافقات

### الفوترة (اختياري في المرحلة الأولى من Portal)
- عرض الفواتير والمدفوعات
- تتبع حالة الدفع
- تكامل مع Stripe أو مزود دفع مماثل

## البنية التقنية المستهدفة

### Authentication
```
Stack: NextAuth.js أو Supabase Auth
النموذج: Multi-tenant — كل عميل يصل لبياناته فقط
المستويات:
  - client: يرى مشاريعه فقط
  - admin: يرى ويُدير كل شيء
```

### Database
```
Stack: PostgreSQL (عبر Supabase أو managed PostgreSQL)

الجداول الأساسية:
  clients (id, name, email, created_at)
  projects (id, client_id, title, status, start_date, expected_end)
  milestones (id, project_id, title, status, due_date)
  deliverables (id, milestone_id, title, file_url, status)
  updates (id, project_id, content, created_by, created_at)
  messages (id, project_id, content, sender_id, created_at)
```

### Frontend
```
Stack: Next.js (امتداد لمشروع المرحلة الثالثة)
Pages الإضافية:
  /portal          → login page
  /portal/[id]     → لوحة تحكم العميل
  /admin           → admin dashboard (auth محمي)
  /admin/projects  → إدارة المشاريع
```

### موقع الـ Portal من الموقع الحالي
```
amer.dev/          ← موقع التموضع (المراحل 1-4 — يبقى كما هو)
amer.dev/portal    ← Client Portal (المرحلة الخامسة)
amer.dev/admin     ← Admin (internal)
```

موقع التموضع لا يتغير. Portal هو إضافة فوقه، لا بديل عنه.

## ما يبقى ثابتاً من المراحل السابقة

| المكوّن | يبقى كما هو | ملاحظة |
|--------|------------|--------|
| Design tokens | نعم | Portal يستخدم نفس النظام البصري |
| React components (موقع التموضع) | نعم | لا تغيير |
| API /api/v1 routes | نعم | تُضاف routes جديدة للـ Portal |
| TypeScript types | موسَّعة | تُضاف types للـ Portal entities |
| CSS architecture | موسَّعة | CSS Modules لمكونات Portal الجديدة |

## شروط البدء

الانتقال للمرحلة الخامسة يُبرَّر حين:
1. عدد العملاء النشطين يجعل إدارة المشاريع بالبريد الإلكتروني غير فعّالة (> 3-5 مشاريع متزامنة)
2. طلبات عملاء متكررة على تحديثات الحالة تستهلك وقتاً غير متناسب
3. API Layer (المرحلة الرابعة) مستقرة ومختبرة

## الفرق بين المرحلة الأولى والخامسة

| | المرحلة الأولى | المرحلة الخامسة |
|-|--------------|----------------|
| الجمهور | مقيّمون محتملون | عملاء حاليون |
| الهدف | إدارة الانطباع | إدارة العلاقة |
| المحتوى | ثابت، تسويقي | ديناميكي، تشغيلي |
| Auth | لا | نعم |
| Database | لا | نعم |

## القيود التي يجب مراعاتها
- Portal يخدم عملاء حاليين — لا يؤثر على تموضع الموقع للمقيّمين الجدد
- التصميم البصري للـ Portal يتبع نفس Design System — لا هوية بصرية منفصلة
- البدء بـ MVP بسيط (حالة المشروع + التسليمات فقط) قبل إضافة الفوترة والمزايا المتقدمة

## التأثير على التطبيق
القرارات في المراحل 1-4 التي تخدم هذه المرحلة:
- JSON schemas المرحلة الأولى تُعرّف أشكال البيانات التي ستُصبح database schema
- TypeScript types المرحلة الثانية تُصبح shared types بين Frontend وBackend
- CSS tokens المرحلة الأولى تُصبح Design System للـ Portal
