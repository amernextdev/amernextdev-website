# client-psychology-model.md

## الهدف
نمذجة كيف يُعالج المقيّم المستهدف المعلومات ويتخذ قرار التواصل.
المنظومة مُصمَّمة لتُرضي هذا النموذج المعرفي، لا نموذج المستخدم العام.

## المشمول
- ملف المقيّم الأساسي والثانوي
- نمط القرار المعرفي المُتّبع
- الاختصارات المعرفية التي يستخدمها المقيّم لتقييم الثقة
- مبادئ العبء المعرفي

## غير المشمول
- آليات التصفية التي تعمل على هذا النموذج (→ `trust-filter-framework.md`)
- إشارات السلطة المحددة (→ `authority-signals-spec.md`)
- الطبقات الثلاث للتموضع (→ `positioning-doctrine.md`)

## ملف المقيّم

### المقيّم الأساسي
صانع قرار يمتلك:
- صلاحية الميزانية
- إلمام تقني كافٍ لتقييم القرارات المعمارية
- مشكلة محددة على مستوى الأنظمة يسعى لحلها

سلوكه: لا يتصفح خيارات. يُجري اجتهاداً حقيقياً على مرشح بعينه قرر الوصول إليه بمساعدة توصية أو بحث مركّز.

### المقيّم الثانوي
حارس تقني (CTO، مهندس رئيسي، مؤسس مشارك تقني) يُشترط موافقته قبل الانخراط.
سلوكه: يفتح DevTools، يقرأ الكود المصدري، يفحص القرارات المعمارية.

**الاستراتيجية للمقيّم الثانوي:** HTML الدلالي، CSS المنظّم، JS الموثَّق — كلها مرئية ومقصودة. الكود نفسه دليل كفاءة.

## نمط القرار المعرفي

المقيّم المستهدف لا يتبع نمط الشراء الاستهلاكي (تصفح → مقارنة سعر → قرار سريع).
يتبع نمط **التدقيق المكثف**:

```
تحديد مشكلة أنظمة
       ↓
بحث عن مرشح محدد (عبر توصية أو بحث مركّز)
       ↓
تقييم المصداقية الأولية (0–3 ث)
       ↓
اجتهاد فعلي في المحتوى والعمق (3–30 ث+)
       ↓
فحص تقني اختياري (source code, performance)
       ↓
قرار التواصل أو المتابعة
```

**النتيجة التصميمية:** المحتوى يجب أن يدعم التدقيق، لا يُبسَّط لتدفق استهلاكي.

## الاختصارات المعرفية للثقة

المقيّم يستخدم إرشادات معرفية لتقييم الثقة في غياب معلومات كاملة:

### إرشاد الاتساق البصري
الطباعة أو التباعد غير المتسق → يُسجَّل كإهمال في الانتباه للتفاصيل.
**التطبيق:** شبكة 8px صارمة، تراتبية طباعية ثابتة، لا قيم اعتباطية.

### إرشاد إشارة الجهد
الاستثمار الظاهر في الموقع يعكس الاستثمار المحتمل في عمل العميل.
**التطبيق:** جودة التنفيذ في كل تفصيلة — الأداء، الكود، المحتوى — مرئية وتُرسل رسالة.

### إرشاد الندرة
إشارات الانتقائية توحي بطلب مرتفع، وبأن الاختيار مُتكافئ (المهندس يختار عملاءه أيضاً).
**التطبيق:** لا توافر مفتوح، لا نماذج عروض فورية، آلية تواصل تُشير إلى عملية.

### إرشاد الكفاءة التقنية
كود نظيف، تحميل سريع، HTML دلالي — مرئية للمقيّم التقني.
**التطبيق:** Lighthouse score عالٍ، source code نظيف، لا جمل CSS فارغة.

### إرشاد دقة اللغة
اللغة الغامضة أو المتحمسة تُدمر المصداقية التقنية فوراً.
**التطبيق:** تحديد تقني ("بنية مكونات React معيارية") لا ادعاء عام ("أبني تطبيقات رائعة").

## مبادئ العبء المعرفي

**كثافة المعلومات تتناسب مع تطور المقيّم.**
المقيّم المستهدف متعلم تقنياً. التبسيط المفرط إشارة ضعف، لا إشارة تواصل جيد.

**كل قسم يجيب على سؤال محدد للمقيّم.**
لا محتوى يتيم. إذا لم تستطع تحديد "ما السؤال الذي يُجيب هذا القسم؟"، يُحذف.

**الإفصاح التدريجي.**
إشارات المصداقية السطحية أولاً. العمق متاح عند الطلب (صفحات مفصلة، حالات دراسة، كود).

**صفر غموض في التراتبية.**
المقيّم يجب أن يعرف دائماً أين هو في الموقع وما القادم. الضياع تجربة مُكلفة معرفياً.

## القيود التي يجب مراعاتها
- هذا النموذج مبني على المقيّم المستهدف، لا على متوسط مستخدمي الويب
- تحسين التجربة لجمهور أوسع قد يعني إضعاف تجربة المقيّم المستهدف — هذا مقايضة واعية
- النموذج ثابت ما دام الجمهور المستهدف ثابتاً

## التأثير على التطبيق
كل قرار في بنية المعلومات والمحتوى يُختبر بالسؤال: "كيف يعالج هذا المقيّم هذا العنصر في سياق نمط التدقيق المكثف؟"
